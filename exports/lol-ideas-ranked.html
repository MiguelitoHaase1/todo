How to read this

All 19 ideas live in the todo store under the LOL: prefix — nothing hand-picked. Scores are judgement calls on a 1–10 scale, shown in full so you can overrule any of them and watch the ranking move.

Updated 26 July 2026. ID 1 renamed “a webhook per project” → “Event Triggers”, here and in the to-do itself. Reframed: the Edge Function primitive already exists — the value is the guided setup layer (endpoint creation, auth/signatures, event mapping, retries, idempotency, monitoring). Demo path: sensor event → endpoint → database record → realtime dashboard → notification → agent action. That re-scoped it from ease 9 / enterprise 8 (8.35) to ease 6 / enterprise 9 (7.70) — harder to build, worth more to a buyer — which moves it to second behind Scheduled actions on score, and build slot 3. IDs stay frozen so earlier references still resolve.

ID 19 added — an official Security Automation CLI: a thin, stable client over the existing Security Center API (trigger/await scans, query findings and freshness, severity thresholds, JSON export, deterministic exit codes for CI or cron), explicitly not a separate scanning system. Pitch: “Security Center as code.” Scored ease 4 / enterprise 9 / wow 6 = 6.50 — ease is held down by the one real blocker, scoped service-account authentication. That prerequisite is also required by #2 and adjacent to #1, so it may be worth more than the CLI it blocks.

ID 5 scope corrected — retitled to “Secret & credential capture guidance”, here and in the to-do. It was rendered too narrowly. The scope is: show the exact secret name, expected format, storage location and live validation at the point of entry — across four surfaces: connector setup, Edge Functions, APIs and BYOK flows. “Fold it into connector onboarding” is rejected; connectors are one surface, not the scope. Scored three times — 9/7/3 (6.70) on the original narrow scope, then 7/8/3 (6.40) when I assumed four surfaces meant per-provider work, then 9/8/3 (7.10) once that assumption was corrected. The guidance is LLM-driven, not procedural: the model generates the step-by-step walkthrough through the provider's own UI, exactly as Claude Code already does, so there is no lookup table of where each vendor hides its keys and no per-provider scripts to maintain. Provider variance costs nothing, so the surface count stops multiplying the work. #5 moves from eighth to fourth.

Build order set 26 July. 5 → 2 → 1 → 15 → 6+7 → 3 → 10 → 19, with 14 in parallel. Michael's rationale: 5 now (small, user-visible, few dependencies) · 2 before 1 (establish one trigger/scheduling substrate, then add external events) · 15 before 6+7 (define eval, compatibility and trust gates before importing or distributing skills) · 3 after 1+2 (outcome loops need triggers, budgets, retries and stop conditions) · 10 before 19 (connector creation is nearer existing work) · 19 last (waits for scoped API keys/service accounts, not because the idea is weak). Ten to-dos are dated Mon 27 – Fri 31 July, with priorities set so same-day items sort in sequence order. The other nine to-dos were dropped — a recoverable status, not a deletion — and all nine ideas remain on this page.

#4 is worth a second look. Lovable MCP accessible IN Lovable was in the previous prioritised ten and is not in the sequence, despite scoring 6.85 — higher than five of the ten that are scheduled. It is the only idea whose status changed from in to out without being discussed.

ID 20 added 26 July — “Lovable builds desktop apps”, NOT in the sequence. Checked against the Company Brain first, which splits the question in two: Lovable as a desktop app already shipped (Electron, macOS + Windows, local MCP servers, launched 14 April, release project completed 5 July), while Lovable emitting desktop apps appears nowhere — not roadmapped, not rejected, simply absent. The wrapper is the easy 20%: Lovable emits a standard Vite dist/. The hard 80% is code signing and notarisation (whose certificate signs a user's app?), per-OS build runners, auto-update channels, distribution, and the fact that a desktop app still calling a hosted backend is a browser in a costume. Sharpening: the valuable version is “Lovable builds apps that can talk to localhost”, and one signed bridge helper divides the signing problem by the number of apps where per-app packaging multiplies it. Scored ease 3 / enterprise 7 / wow 9 = 6.10. A proof of concept is LOL-week-sized; a production desktop target is a quarter.

These are 20 distinct items. Dependencies and sequencing between them are noted where they exist — a dependency is not a merge. No idea here should be folded into another.

  • Ease of execution — how much platform work stands between the idea and a shippable version. 10 = a week and a design review. 1 = a new subsystem plus a security argument.
  • Value for enterprises — does this unlock or expand an enterprise deal. Governance, integration into an existing stack, and unattended operation score high; local-machine access scores low, because it is the thing security teams block first.
  • Wow effect for Lovable management — how agentic and future-facing the idea reads to the people who set roadmap. Rewards ideas that change what Lovable is, not what it does faster.
  • Quadrants split at 6 / 6. “Do now” is high on both. “Worth the build” is the enterprise value you have to pay for. “Park it” is where two ideas honestly sit.
